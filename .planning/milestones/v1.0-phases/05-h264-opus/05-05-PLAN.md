# Phase 5 Plan 05: 固定媒体 Fixture、双向 Harness 与收口

<objective>
用固定 H264 Annex-B 和 Opus length-prefixed fixture 证明 Phase 5 双向编码后媒体路径可观察：C 端发送 H264/Opus frame 进入 RTP/SRTP，接收路径输出 H264 Annex-B 和 Opus payload frame，RTCP NACK/PLI 行为可见，并更新文档、路线图、状态和来源追溯。
</objective>

<must_haves>
<truths>
- D-15: Opus fixture 使用长度前缀 + Opus packet 序列，不引入 Ogg parser。
- D-16: Opus 接收验证到编码后包层，断言非空 payload 和 timestamp 单调。
- D-08: 固定 H264 测试流应在关键帧前自带 SPS/PPS，不新增 extradata API。
- D-19/D-20: Phase 5 使用分层 C harness 证明 packetize、depacketize、SRTP media integration 和 `on_frame` 输出；不把完整 Chrome 自动化 E2E 当作 Phase 5 完成标准。
- MEDIA-07: C 端 E2E 发送媒体源必须支持读取固定 H264/Opus 测试文件。
</truths>
</must_haves>

<threat_model>
| Threat | Severity | Mitigation |
|--------|----------|------------|
| Fixture 不含真实编码后边界，媒体路径测试退化成随机 bytes | HIGH | H264 fixture reader asserts Annex-B SPS/PPS/start code；Opus reader asserts length-prefixed non-empty packets。 |
| Harness 只覆盖发送或只覆盖接收，双向要求未达成 | HIGH | Verifier labels separately assert H264 send/receive and Opus send/receive。 |
| 文档误导 Phase 5 已完成 Phase 6 Chrome 自动化 | HIGH | README/ROADMAP/STATE 明确 Phase 5 是 C fixture harness，Chrome automation remains Phase 6。 |
</threat_model>
