# Phase 6 Plan 08: 真实 DTLS/SCTP Transport 依赖解锁与严格 Smoke 收口

<objective>
在 06-07 已完成 STUN/ICE polling 和假阳性防护的基础上，解锁严格 transport 依赖，并补齐真实 OpenSSL DTLS packet BIO、DTLS-SRTP key export、usrsctp/DCEP packet IO 和 PeerConnection packet pump。完成后，严格命令 `MRTC_E2E_REQUIRE_TRANSPORT=1 MRTC_E2E_BROWSER_CHANNEL=chromium npm --prefix tests/e2e run test:host -- --grep "transport smoke"` 必须在浏览器侧达到 `connection: "passed"`、`datachannel: "passed"`，并证明真实 `ping:<nonce>` / `pong:<nonce>` 往返。
</objective>

<gap_source>
本计划来自 `--gaps` 缺口收口。Phase 06 当前没有 `06-VERIFICATION.md`，缺口来源采用已执行的 `.planning/phases/06-chrome-e2e/06-07-SUMMARY.md`、`.planning/phases/06-chrome-e2e/06-03-SUMMARY.md` 和 `.planning/debug/chrome-transport-smoke-blocks.md`：

- 06-07 已让 classification smoke 通过 signaling，并防止 `addIceCandidate` / in-process callback 伪造 DataChannel open/message。
- 06-07 self-check 失败：strict smoke 仍记录 `connection: "blocked"`、`datachannel: "blocked"`、`failure_stage: "connection"`。
- 当前环境严格 configure 仍缺 `libsrtp` 和 `usrsctp`；OpenSSL 可用。没有这些依赖时不得宣称真实 Chrome transport 完成。
- `src/dtls/dtls_session.c` 仍未实现真实 DTLS packet BIO handshake；`src/sctp/sctp_session.c` 仍未把 usrsctp packet IO 接到 DTLS application data；`src/peer_connection.c` 对非 STUN DTLS packet 仍返回 `MRTC_STATUS_NOT_IMPLEMENTED`。
</gap_source>

<must_haves>
<truths>
- Chrome 侧 `RTCPeerConnection.connectionState === "connected"` 是连接成功门槛；C 内部 `pc.connected` 只能作为诊断事件。
- DataChannel 成功必须由浏览器真实收到 `pong:<nonce>` 证明，不允许通过 C 内部 loopback callback 伪造。
- 严格 transport 构建必须依赖 OpenSSL、libsrtp 和 usrsctp；缺依赖时任务阻塞并输出明确本地安装提示。
- 本地 KVS 参考只能来自 `reflib/kvs-webrtc-sdk`，优先参考 `src/source/Crypto/Dtls_openssl.c`、`src/source/Sctp/*`、`src/source/PeerConnection/DataChannel.*` 和 `src/source/Ice/*`。
- 核心 `micrortc` target 可以链接协议依赖，但不能引入 KVS signaling、AWS credential/storage、libwebsockets、GStreamer、FFmpeg 或媒体采集/编码。
</truths>
</must_haves>

<threat_model>
| Threat | Severity | Mitigation |
|--------|----------|------------|
| 缺 `libsrtp` / `usrsctp` 时继续执行并得到假通过 | HIGH | 06-08-01 必须先通过 `MRTC_REQUIRE_SYSTEM_TRANSPORT_DEPS=ON` configure；失败时停止执行后续 DTLS/SCTP 任务。 |
| DTLS 仍通过 `set_verified_peer_fingerprint()` 直接 connected | HIGH | DTLS connected 只能由 OpenSSL handshake 完成和 peer certificate fingerprint 校验触发。 |
| SRTP key 仍来自固定 seed / hash filler | HIGH | keying material 必须来自 `SSL_export_keying_material(..., "EXTRACTOR-dtls_srtp", ...)`。 |
| DataChannel pong 仍来自本地 loopback | HIGH | `pong:<nonce>` 必须经 browser DataChannel -> SCTP -> DTLS -> C callback -> DTLS -> SCTP -> browser DataChannel。 |
| 从 KVS 搬迁时带入 signaling/AWS credential | HIGH | 只引用本地协议层文件；`SOURCE-MANIFEST.md` 必须排除 `src/source/Signaling` 和 samples credential。 |
</threat_model>

把 `MRTC_DTLS_SESSION` 扩展为真实 OpenSSL DTLS session：保存 `SSL_CTX`、`SSL`、input/output memory BIO、local certificate/key、role、remote fingerprint expected value 和 handshake state。新增 packet-oriented API：`mrtc_dtls_session_set_remote_fingerprint()`、`mrtc_dtls_session_start()`、`mrtc_dtls_session_handle_inbound_packet()`、`mrtc_dtls_session_drain_outbound_packet()`、`mrtc_dtls_session_is_connected()`、`mrtc_dtls_session_export_srtp_keying_material()`。answerer 根据 remote SDP `a=setup:actpass/active/passive` 选择 server/client role；connected 只能在 `SSL_is_init_finished()` 且 peer certificate SHA-256 fingerprint 等于 remote SDP fingerprint 后置位。删除真实 Chrome 路径上的 hash filler keying material，改用 `SSL_export_keying_material(..., "EXTRACTOR-dtls_srtp", ...)` 导出 60 bytes SRTP key/salt。
</action>
<verify>
<automated>`cmake --build build-transport && ctest --test-dir build-transport -R "dtls|srtp" --output-on-failure`</automated>
</verify>
<acceptance_criteria>
- `mrtc_dtls_session_export_srtp_keying_material()` 在 handshake 完成前返回 `MRTC_STATUS_INVALID_STATE`。
- `test_dtls_srtp.c` 覆盖 client/server memory BIO packet exchange，直到双方 `mrtc_dtls_session_is_connected()` 为 true。
- `test_dtls_srtp.c` 覆盖 remote fingerprint mismatch，并断言 session 进入 failed 或返回 `MRTC_STATUS_INVALID_STATE`。
- `test_dtls_srtp.c` 在 `MRTC_HAVE_SRTP=1` 时证明 libsrtp protect/unprotect 使用 DTLS 导出的 key/salt；严格 build 不允许 passthrough 被当作成功。
</acceptance_criteria>
</task>
