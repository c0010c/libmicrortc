# Phase 6 Plan 02: C Answerer Demo、结构化事件与固定媒体源

<objective>
实现 `mrtc_chrome_answerer` C demo，使它通过 line-delimited JSON 接收 Chrome offer/candidate、返回 answer/candidate、创建 DataChannel 和 H264/Opus transceiver、读取固定媒体 fixture 向 Chrome 发送编码后帧，并把连接、DataChannel、C 侧收到的 browser 媒体帧和候选路径输出为结构化事件。
</objective>

<must_haves>
<truths>
- D-03: Demo 主路径是 C answerer。
- D-07: C 端媒体接收证明必须到 `on_frame` 回调层，记录 kind、codec、count、bytes 和 timestamp monotonic。
- D-08: C 端不能只收到一个 packet 就宣布成功；至少用 count 和 timestamp 增长证明短时稳定流动。
- D-10: 本地 ICE/TURN credential 不出现在 stdout、stderr、summary 或 README。
- E2E-05: DataChannel 双向消息要经过 demo 回调，而不是只检查 API compile。
</truths>
</must_haves>

<threat_model>
| Threat | Severity | Mitigation |
|--------|----------|------------|
| Demo 输出真实 TURN secret | HIGH | 所有 config/event/log 输出调用 redaction helper；测试用 secret fixture 验证 stdout 不含明文。 |
| C 端媒体证明停留在 RTP packet 层 | HIGH | Demo 统计 public `on_frame` 回调，输出 `media.frame` 事件。 |
| C demo 误用 private API 破坏 public API 验收价值 | MEDIUM | 默认使用 public headers；若必须新增诊断 API，放入 public read-only API 并用 package consumer 覆盖。 |
</threat_model>
