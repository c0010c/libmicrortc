# WebRTC 纯 C 库设计边界记录

本文记录截至目前已经确认的首版设计边界与关键决策，作为后续架构/API 设计文档和实现拆分的输入。

## 目标

设计一个跨平台、运行在性能受限设备上的生产级 WebRTC 库。

- 语言：纯 C。
- 互通目标：与 Chrome 完成 1v1 音视频通话。
- 编解码边界：库本身不处理音视频编解码。
- 线程边界：库本身不创建线程。
- 内存边界：内存占用在创建阶段固定下来，运行期不动态增长。
- API 方向：尽量靠近浏览器 WebRTC API。
- 可观测性：首版就需要具备较强的生产排障能力。

## 已确认决策

| 主题 | 决策 |
| --- | --- |
| 首版边界 | 提供完整 `PeerConnection`，库负责 SDP/JSEP、ICE、DTLS-SRTP、RTP/RTCP。 |
| 内存模型 | 用户传入总 arena 和 limits，库在创建时一次性切分，之后不动态增长。 |
| 执行器模型 | 提供 `signaling`、`media`、`network` 三个 `post + timer` 执行器抽象。 |
| 网络边界 | 用户负责 UDP/socket 收发，库只处理 datagram 输入输出。 |
| 媒体边界 | 用户输入/接收 H264 access unit 和 Opus frame，库负责 RTP 打包/解包。 |
| H264 | 发送仅支持 single NALU / FU-A，接收有限支持 STAP-A。 |
| RTCP | 支持 SR/RR、SDES、PLI；NACK 解析并上报，不做重传。 |
| ICE | 支持 Full ICE + STUN，支持 host/srflx，不支持 TURN。 |
| SDP/JSEP | 采用 Chrome 1v1 最小画像，支持 BUNDLE、rtcp-mux、DTLS fingerprint/setup、ICE 参数、H264、Opus。 |
| 加密 | DTLS/SRTP/crypto 使用可插拔 backend vtable。 |
| 可观测性 | 提供事件、计数器、trace hook。 |
| API 风格 | 核心对象使用不透明句柄，错误使用 `rtc_status_t` 返回码。 |
| 并发契约 | 采用执行器亲和模型。 |
| 通话角色 | 支持发起和接听，即支持 createOffer/createAnswer。 |
| 媒体方向 | 重点支持 `sendrecv` / `recvonly`。 |
| 媒体规模 | 单个 `PeerConnection` 最多 1 路音频 + 1 路视频。 |
| RTP 扩展 | 支持最小必要扩展；拥塞控制相关扩展只解析/统计。 |
| 事件模型 | 使用统一 observer vtable。 |
| ICE 交互 | 支持 trickle ICE。 |
| 平台抽象 | 使用统一 platform vtable。 |
| 交付形态 | 使用 CMake 静态库。 |
| 验收方式 | 使用本地 Chrome 页面 + 信令示例完成 1v1 音视频通话。 |
| 依赖策略 | 宽松许可优先，避免 GPL/LGPL。 |
| 下一交付物 | 架构/API 设计文档。 |

## 设计含义

### 完整 PeerConnection

首版对外提供接近浏览器 WebRTC 的 `PeerConnection` 体验。用户不需要直接编排 ICE、DTLS、SRTP、RTP/RTCP 和 SDP/JSEP 状态机，但库内部仍应按这些子系统拆分，避免核心对象变成不可维护的巨大状态机。

### 固定内存

用户在创建 `PeerConnection` 时传入一块总 arena 和能力上限。库根据 limits 在创建阶段完成对象、队列、候选、包缓存、SDP 缓冲区等内存切分。创建成功后，运行期不得依赖动态内存增长。

### 无内部线程

库不创建线程，也不拥有平台事件循环。库通过三个执行器抽象投递任务和定时器：

- `signaling`：负责 SDP/JSEP、用户 API 状态推进和信令相关事件。
- `media`：负责编码帧输入输出、RTP packetize/depacketize 和媒体状态。
- `network`：负责 ICE、DTLS、SRTP、UDP datagram 输入输出和网络定时器。

用户可以把三个执行器映射到三个线程，也可以多个执行器映射到同一个线程/task/superloop。

### 用户负责网络 I/O

库不直接创建或操作 socket。库通过事件或回调输出待发送 UDP datagram，用户负责实际发送。用户收到 UDP datagram 后，再调用库的输入函数交给库处理。

### 编码帧级媒体 API

库不处理 H264/Opus 编解码。发送方向，用户向库提交 H264 access unit 或 Opus frame；接收方向，库输出 H264 access unit 或 Opus frame 给用户解码。RTP payload format、时间戳、序列号、SRTP 加解密由库负责。

### Chrome 最小互通画像

首版只追求 Chrome 1v1 音视频通话所需的最小 SDP/JSEP 能力，不追求广泛 SDP 兼容。核心能力包括 BUNDLE、rtcp-mux、DTLS fingerprint/setup、ICE 参数、H264、Opus 和 trickle ICE。

### 不做拥塞控制

首版不实现拥塞控制。与拥塞控制相关的 RTP header extension 可以解析、统计或 trace，但不进入码率控制、发送节奏控制或带宽估计闭环。

### 可插拔加密后端

DTLS/SRTP/crypto 不在核心 API 中绑定特定第三方库，而是通过 backend vtable 注入。首版参考适配优先选择宽松许可依赖，并避免 GPL/LGPL。

### 强可观测性

首版需要具备生产排障基础能力，包括：

- 状态事件。
- 错误事件。
- 关键计数器。
- trace hook。
- NACK 等未执行动作的可观测上报。

## 后续待细化项

- `rtc_peer_connection_config_t`、arena、limits、platform vtable、executor vtable、observer vtable 的具体结构。
- `rtc_status_t` 错误码集合和错误分类。
- `createOffer`、`createAnswer`、`setLocalDescription`、`setRemoteDescription`、`addIceCandidate` 等 API 的具体签名。
- UDP datagram 输入输出 API 的所有权、生命周期和执行器亲和规则。
- H264/Opus 编码帧结构、时间戳单位、关键帧标记和丢帧语义。
- SDP Chrome 最小画像的精确定义和兼容策略。
- ICE candidate 上限、STUN server 配置、连接检查状态机和失败超时。
- DTLS/SRTP backend vtable 的职责边界和参考实现选择。
- RTP header extension 最小集合的具体列表。
- 计数器、事件、trace hook 的命名、字段和稳定性策略。
- 本地 Chrome 页面、信令示例和端到端验收流程。
